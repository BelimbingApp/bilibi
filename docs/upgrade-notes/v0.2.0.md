## Pull request 102: fix(artifacts): create a default document folder and widen Settings reads

https://github.com/BelimbingProject/bilibi/pull/102

Settings read methods now take `&dyn bilibi_tenancy::ReadClient`. Update wrappers that accept only a PostgreSQL `GenericClient` or a `ProofClient` when they forward that client to Settings:

```rust
// Before
async fn layout(client: &(impl tokio_postgres::GenericClient + Sync), settings: &Settings) { /* ... */ }
// After
async fn layout(client: &dyn bilibi_tenancy::ReadClient, settings: &Settings) { /* ... */ }
```

PostgreSQL clients and transactions have blanket implementations and need no adapter. Pass an operation’s handed client directly; do not open a pooled connection. For custom `OperationClient` implementations, move `query` into `impl ReadClient`, keep the existing `ProofClient` implementation, and leave `impl OperationClient` as the marker implementation. Settings writes still use `MutationTransaction`.

Run `bilibi-web seed-production` during the upgrade to initialize the missing Artifacts storage path. Existing values, including explicitly cleared ones, are preserved. Back up the saved private storage directory with its metadata. Use the shared flash component without page-owned positioning.

Artifacts adds `Error::MissingRoot(String)` for a missing custom directory. Preserve its folder and settings guidance in a Domain’s refusal instead of reducing it to a generic storage code. The Finance companion updates its Attachments mapping and pages for this case.

## Pull request 120: add a page search to the top bar

https://github.com/BelimbingProject/bilibi/pull/120

Nothing breaks, and no code change is needed to keep building. The new top-bar search lists Domain and Extension pages automatically, from their existing `Route` contributions, page titles and menu rows. **A page is found by the top-bar search only if `Page::title` returns its name or it has a menu row.** To make your pages findable, have your agent:

1. List your page routes: `Route` contributions with `Method::Get` and no `{parameter}` in the path. Pages with a path parameter (a record's own page) are never listed and need nothing.
2. For each route a person should be able to find, make `Page::title(operation)` return the page name alone, for example `"Create Invoice"` (the host adds the product suffix), or give the route a menu row. A page with neither is not found.
3. For a route that only redirects (`Page::redirect(operation)` returns `Some`): if it is a real destination, such as a create page that opens a dialog on its list, keep its title; it is listed only for people who may also open where it leads. If it only keeps an old address working, return `None` from `title` for it, or replace it with a `Moved` contribution (`apps/web/README.md`), which the search never lists.
4. Make each route's `Access` match what the page itself requires. The search judges a page by its route's access, as the menu does, so a page that refuses some people its route admits (an extra check in `render` or `mount`) is listed for them and answers 403.
5. Check it: run the app, press `/` outside a field (or click the search icon before the bell) and type each page's name, signed in once as a person who may open it and once as one who may not.
