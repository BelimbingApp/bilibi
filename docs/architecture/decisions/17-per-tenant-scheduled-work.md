# ADR 17: One global schedule, fanned out under per-tenant consent

**Document Type:** Architecture Decision Record
**Status:** Proposed
**Agents:** codex/gpt-6
**Scope:** How `base/schedule` dispatches one recurring definition to tenant-local Queue jobs
**Last Updated:** 2026-10-30

> Source: [issue 138](https://github.com/BelimbingProject/bilibi/issues/138). The existing Schedule and Queue contracts are in [`apps/base/schedule/README.md`](../../../apps/base/schedule/README.md) and [`apps/base/queue/README.md`](../../../apps/base/queue/README.md).

## Context

`base/schedule` currently stores one installation-global definition and claims an occurrence in the platform operator's tenant. Its worker is queued in that tenant. A Domain cannot enumerate tenants: tenant listing requires an `OperatorProof`, and direct SQL against Tenancy's tables would break ownership and authorization boundaries. `Queue::enqueue_system` already runs one job as a named principal in one tenant and re-proves tenant activity, principal declaration and durable grant on every attempt.

Report schedules, privacy retention sweeps and tenant-local operational jobs need the same recurrence to run separately against each tenant's records. Copying one cron definition per tenant would duplicate operator review and fingerprint state. A worker that reads or writes all tenants itself would bypass Queue's sealed tenant scope and make one tenant's failure block the others.

## Proposed contract

This proposal makes the Queue policy, operator-tenant inclusion, ledger/child-row ownership, and global start-gate decisions explicitly; none of those choices is deferred. It is the architecture source for the per-tenant contract summarized in the Schedule module README.

1. A schedule definition declares `Reach::Installation` or `Reach::EachTenant`. `Installation` remains the default and preserves current behavior. Reach is part of the definition fingerprint; changing it invalidates the existing review.
2. The scheduler claims one `EachTenant` occurrence in the operator tenant as it does today. A Platform-owned fan-out dispatches tenant jobs; the owner module's worker never enumerates or writes across tenants itself.
3. Per-tenant system work uses the separate tenant-audience capability `bilibi_schedule::TENANT_EXECUTE` in customer tenants. The platform operator tenant is included as an `EachTenant` target and uses platform `bilibi_schedule::EXECUTE`; this is an explicit decision, not inferred from enumeration. The existing `EXECUTE` cannot authorize the scheduler in a customer tenant and remains platform-only. The Schedule vocabulary declares both capabilities, and the `scheduler` system principal's declared capability set includes both `EXECUTE` and `TENANT_EXECUTE`; Authz refuses an undeclared system-principal capability before it checks grants ([`apps/base/authz/src/lib.rs`](../../../apps/base/authz/src/lib.rs)). Declarations and provisioning grant `TENANT_EXECUTE` nowhere by default. Each tenant must have the applicable grant; this follows per-tenant consent, not ADR 12's standing-grant exception.
4. Tenant discovery stays in Tenancy and uses a dedicated once-bound `ScheduleTenantAuthorizer`, implemented by Authz rather than broadening `OperatorAuthorizer`. The Schedule-only API is `Tenants::scheduled_page(scope, after_id, through_id, limit) -> ScheduledTenantPage`. Tenancy proves the sealed scope is the declared `scheduler` system principal in the active platform-operator tenant and rechecks `admin.tenancy.schedule.fan_out` with platform audience on every page. It does not create an `OperatorProof`: that proof is intentionally refused to system principals. `SystemScope` alone is not authority to enumerate tenants. The directory returns only tenant ID, active/suspended status and `is_platform_operator`; it excludes deleted tenants, orders by ID, accepts an exclusive `after_id` and fixed high-water `through_id`, and rejects limits outside `1..=200`. Tenancy has no Schedule dependency.
5. Fan-out stores the high-water ID and last fully resolved ID on the operator-side occurrence progress. The first page captures the high-water mark; tenants created later join the next occurrence even if creation precedes completion of the current fan-out. It processes at most 200 targets per page and advances the cursor only after every target in that page has a durable outcome. Concurrent fan-out attempts may read the same page: compare-and-set cursor advancement plus unique `(occurrence_id, tenant_id)` ledger and tenant-run keys makes them converge. A retry reconciles an existing tenant-run/job before advancing; it never holds an operator transaction open while writing a tenant transaction. Each active target is checked through Authz's narrow `scheduled_execution_decision(operator_scheduler_scope, tenant_id)` API, which selects platform `bilibi_schedule::EXECUTE` for the marked operator tenant and tenant `bilibi_schedule::TENANT_EXECUTE` for customer tenants. It uses Authz's normal direct-deny precedence and decision logging and returns an explicit allow/deny result. Infrastructure errors abort the page for retry and are never counted as `not_granted`. Schedule does not read grants or duplicate Authz logic. Allowed tenants get jobs; suspended tenants are `skipped`; tenants with an explicit deny are `not_granted`; deleted tenants are excluded.
6. For each tenant, a single audited `MutationBoundary` transaction inserts a unique tenant-run row and inserts the child job in Queue: scheduled system jobs use `Queue::enqueue_system`; tenant-user manual jobs use `Queue::enqueue_for`. The aggregate row is unique by `(occurrence_id, tenant_id)` for scheduled runs or `(request_id, tenant_id)` for manual runs. It stores the exact Queue job ID, definition key/fingerprint, trigger, tenant, requester when applicable, status, timestamps and bounded failure code. Use conflict-safe insertion (`ON CONFLICT DO NOTHING RETURNING`); on conflict lock/read the existing row and reconcile its linked Queue job through a status lookup scoped to that tenant. Never blindly enqueue a replacement. If the linked job exists and is nonterminal, retain the link and reconcile; terminal `completed`, `cancelled` or `discarded` maps to the terminal aggregate outcome. A missing job becomes `failed` with `linked_job_missing`; only explicit audited repair may create replacement work. Retryable Queue jobs remain linked. An insert or enqueue error rolls back both writes.
7. **Queue policy decision:** The current Queue binding accepts one capability per handler; it cannot express these modes yet. Queue gains a typed actor-and-audience `CapabilityPolicy` on the existing owner `Worker`/`HandlerBinding`; Schedule continues to register its owner's existing worker and handler, so Queue's same-module ownership validation is unchanged. For this worker, the policy has exactly four explicit slots: system actor in platform-operator tenant -> `bilibi_schedule::EXECUTE`; system actor in customer tenant -> `bilibi_schedule::TENANT_EXECUTE`; user actor in platform-operator tenant (operator Run now) -> `bilibi_schedule::EXECUTE`; user actor in customer tenant (tenant Run now) -> `admin.schedule.tenant.execute`. Queue resolves one slot from the rehydrated identity kind and Tenancy-provided sealed tenant classification, never request arguments, then persists that exact selected key on the job. Before handler invocation, Queue rehydrates the identity, verifies the persisted key still matches the binding policy and current classification, and asks Authz to decide that exact key; it never tries another slot. `Execution` captures the key and identity, and `Execution::begin` re-proves both and asks Authz to decide the same key inside the business transaction. Authz remains the only capability decision implementation, preserving direct-deny precedence and decision logging. A missing, stale or disallowed persisted key fails closed. This is not a Queue-wide OR/AnyOf policy: policy variants must be typed, exhaustive, and resolve exactly one capability or refuse. Queue schema/API changes are required; preexisting jobs with no selected key are refused, never guessed. Owners remain responsible for idempotent effects because Queue is at least once.
8. Before child owner code begins, Queue opens the schedule worker's existing execution path; Schedule then calls a narrow `GlobalEligibility::start(scope, definition_key, fingerprint, child_id)` facade. That facade obtains a scheduler `SystemScope` for the platform-operator tenant from Tenancy's `platform_operator` marker, verifies the declared principal, and authorizes platform `bilibi_schedule::EXECUTE` through Authz. It never derives operator scope from the child scope. In one short operator-tenant audited transaction, it acquires `pg_advisory_xact_lock(hashtextextended('schedule:' || key, 0))`, reads the current reviewed fingerprint and enabled/paused state, and creates the durable start marker only when eligible. Every review, enable, disable, pause, resume and fingerprint mutation acquires the same lock and commits before releasing it. The marker commit is the linearization point: if the change commits first, start is refused; if the marker commits first, that child is considered started and may finish. The gate authorizes on first start only. A later Queue retry with the same child ID and existing start marker is continuation of that already-started child, not new unstarted work, so a later disable does not strand it; Queue and Authz still recheck the exact persisted tenant execution capability on every attempt, and tenant suspension or grant revocation can refuse it. A child without a marker must pass the global gate before any attempt enters owner code. Lock order is operator eligibility transaction (commit/release), then one tenant-local execution transaction; they are never held simultaneously. A crash after marker commit leaves a started marker and queued child row; retry continues that child, while terminal or missing jobs are reconciled without replacement.
9. There are two deliberately different records. The operator-side fan-out ledger is authoritative for cohort pagination, consent outcomes where no tenant row may be written (`suspended` -> `skipped`, explicit grant deny -> `not_granted`), and global eligibility start markers. The tenant-local child-run row is authoritative for the Queue job link, execution lifecycle, requester, and per-tenant overlap; it uniquely keys `(occurrence_id, tenant_id)` and only queued/running rows participate in the `(definition_key, tenant_id)` active-overlap index. Its statuses are `queued` for available/scheduled/retryable Queue states, `running` for executing, `succeeded` for Queue completed, `failed` for terminal cancelled/discarded or missing linked jobs, and `skipped` for per-tenant overlap, with a bounded failure code where applicable. A retryable failed attempt is not aggregate failure. The ledger references the tenant row/outcome for consented tenants; it does not keep a second mutable copy of tenant execution status. Operator board counts join/project the tenant-run lifecycle with ledger outcomes; if a started ledger marker has no tenant child row, reconciliation records failed delivery without re-enqueueing. `base_schedule_runs` remains per-attempt evidence and includes `tenant_id`.
10. Forbid-overlap under `EachTenant` is per `(definition key, tenant)`; Installation-reach keeps the current global overlap key and partial unique index. EachTenant stores its own partial unique active key for unfinished `(definition_key, tenant_id)` rows. A slow tenant does not block other tenant jobs. A changed, disabled, paused or unreviewed definition prevents unstarted work from beginning. Queue's per-attempt grant and tenant checks cancel pending work after revocation or suspension; completed effects are not rolled back.
11. Tenants are considered at fan-out time. A tenant created later participates on the next occurrence; there is no backfill. Missed occurrences continue to coalesce once at claim time. Tenant-local wall-clock schedules, tenant-specific cron/pause settings and per-company fan-out are out of scope.
12. Operator Run now fans out one manual occurrence. A tenant administrator may request one tenant-local manual run under `admin.schedule.tenant.execute`; that job runs as the requesting person and does not create a system grant. Schedule generates a request ID server-side after deriving tenant and actor from the authenticated sealed scope; the browser cannot supply the ID or override either identity. It records one tenant-local child-run row with `trigger=manual`, request ID, requester, tenant, definition fingerprint and exact Queue `job_id`, committed with the job in the same audited transaction. `Schedule::run` validates that row, tenant and persisted requester against the Queue identity. Installation runs continue to validate against `base_schedule_occurrences`.
13. Operator history reports `queued`, `running`, `succeeded`, `failed`, `skipped` and `not_granted` per occurrence and supports authorized tenant filtering. Tenant-scoped access to Schedule definitions and history uses this same board/home, with authorization deciding which records and actions each actor can see; it is not a separate tenant page. Retention covers global occurrence data and tenant run history.

The public `Definition` addition and Schedule worker-ID set are source-breaking changes for callers that enqueue Schedule workers. Update all in-repository callers in the same change and use the clean-break policy for official Domains, including companion PRs and upgrade notes where required. Do not add a compatibility field, alias, wrapper or deprecated copy. The next Schedule migration ID must be selected from the registry: `base-schedule-003-schedule-timing` already exists, so `base-schedule-003-tenant-runs` is unavailable.

## Consequences

- One operator review governs when and what the task runs; each tenant separately decides whether the named system principal may run it there.
- The operator tenant participates in `EachTenant` alongside customer tenants; its system job requires platform `EXECUTE`, while customer system jobs require tenant `TENANT_EXECUTE`.
- Fan-out can resume after process failure without duplicate child jobs, and each tenant's work, audit attribution, history and failure lifecycle stays tenant-local.
- Schedule and Domains do not gain general tenant-listing authority or perform cross-tenant SQL. Tenancy owns tenant enumeration through a system-only, capability-checked binding; Queue owns per-attempt job authorization.
- Work-calendar arithmetic remains the owner's responsibility under the Core work-calendar contract when available. Schedule does not interpret tenant business time.
- The operator and tenant audiences use one Schedule board/home, consistent with [`DESIGN.md`](../../../DESIGN.md) (“One thing one door, one door many keys”); authorization determines which records and actions each actor can see.

## Alternatives rejected

- **One schedule registry entry per tenant:** multiplies cron definitions, review state and fingerprints without changing the task's global timing.
- **Owner module loops over tenants:** grants Domains cross-tenant enumeration and bypasses Queue's tenant scope and retry lifecycle.
- **One operator-tenant job writes into every tenant:** makes cross-tenant writes part of one job, audit context and failure boundary, instead of isolated tenant work.
- **Standing grant for all tenants:** conflicts with the issue's explicit per-tenant consent and silently authorizes work during provisioning.

## Out of scope

- This proposal does not define tenant-local wall-clock firing, per-tenant schedules or per-tenant pause controls.
- This proposal does not define per-company fan-out or make Queue's at-least-once delivery exactly once.
- The runtime and UI behavior is not implemented by this ADR; the record remains Proposed until the owner accepts the decision and the feature is built.
