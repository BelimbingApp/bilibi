# Project agent memory

This file is the project's committed home for project-intrinsic agent knowledge: build, test, release, architecture, and sharp-edge notes that should travel with the code.

- Correct entries that work proves wrong; add new ones only by deliberate maintainer choice, never as routine task output.

## Any module under `apps/`

Read this before editing a page, an event handler or a facade. The component that can make a mistake impossible owns the rule: follow its doc comment and its README. This note holds what no component owns. It mirrors the parts of Bilimbi `apps/AGENTS.md` that apply to Rust.

- Take the person who performed an operation (approver, overrider, requester) from the sealed `Scope` (`Scope::actor`, `Scope::mutation_context`), never from an argument, a form field or an ID you look up yourself. A facade that accepts an actor or tenant ID checks whoever the caller names.
- Unattended work (a queued or scheduled job) runs as a named system principal under the `Scope` Queue seals for it (`Execution::scope()`, `apps/base/queue/README.md`), never a borrowed user's scope and never a `_in(tenant, …)` bypass of a facade. Declare the principal in your vocabulary; an administrator grants it by name. The scope's `user()` is `0` and its writes read `System · <principal>`; a facade needs no principal branch unless its reach is per company (`organisation::authorize_target` already treats a granted principal as tenant-wide).
- The company a page or report operates on is `Scope::current_company()` (the session's chosen company, else the affiliation), never `Scope::actor().organisation()`, which is the affiliation and the input to reach: a person who may act in several companies switches in the top bar, and a page that reads the affiliation ignores the switch. Keep reading the affiliation only to decide reach or to bind a record to the person's employer, and keep `bilibi_company::authorize_target` on every read and write: the choice grants nothing (`apps/core/company/README.md`, "The current company"). A live page is bound to the company it opened in and reloads when the session switches, so never cache the company across events.
- A live event checks its own capability first, before any work, and refuses with the page's own message (Bilimbi `authorize_event`, `permitted?/3`).
- A write into a record that belongs to a company authorizes that company with `bilibi_company::authorize_target(client, scope, company, capability)`, not `authorize_key` alone. The key says the actor may do the operation; `authorize_target` also says they may do it in that company (their own, or any with `admin.company.tenant-wide.manage`). Do it in the shared owner path that the page, API, MCP and any bulk caller reach, and in its preview (`core/affiliation` `identity.rs` is the model).
- Recheck the capability in the owner's mutation transaction. The host checks route access before you render, but a mount-time flag that hides a control is presentation, not authority; a stale page can still send the event (`apps/web/README.md`). Do not copy the host's session or route checks into a handler.
- A page that two capabilities open (Bilimbi `{:any_of, [..]}`, Progression's My standing) is a route with `Access::AnyOf(&[..])` and a menu leaf with `Requirement::AnyOf`, never `Access::SignedIn` plus a hand-written check, which boot cannot validate and the menu cannot hide. Each section and write inside still enforces its own capability.
- A control or field that is absent says why and what to do next: `EmptyState::missing`/`forbidden` or the table's empty slot, never a silent `if` that removes it. A field some readers must not see is restricted by an operator at run time through Authz masking (`apps/base/authz/README.md`), not by a capability in code; build the read model through the masking API and refuse writes to a restricted field.
- Render an instant through `bilibi_datetime` (`Rendered`) so the reader's saved clock and timezone apply. Pin a display only for a context of your own. Never label a database session-local time as UTC; read and format time through `bilibi_datetime` (an H6 proof labelled Asia/Kuala_Lumpur session time as UTC).
- Display a money or quantity decimal at the scale it was entered or stored with (`47.60`, not `47.6`; `5 %`, not `5.0000 %`); an empty total is `0.00`; round half up as Bilimbi's `Decimal.round/2` does, never half to even. No shared formatter owns this yet: `Numbers::decimal` (`apps/base/locale`) rounds half to even when given `fraction_digits`.
- Reach agents through an `agent_api` contribution (`apps/base/agent_api/README.md`), a route through a `Route` contribution, a download through `DOWNLOADS`, a file through `Media`. Add no per-module endpoint and no host-router entry (`apps/web/README.md`).
- For editable write reviews in a chat host, use the shared `review_entries` MCP App (`apps/base/agent_api/README.md`, "MCP Apps"). A specialized read card registers one `bilibi_agent_api::App` under `APPS` with `AppSource::Operation` naming its own read operation and stays self-contained: it calls `read`, `plan` and `commit` through the host and never frames a Bilibi page or loads a script from elsewhere. Do not add a tool to `agent_api/src/mcp.rs` or a route for it (`apps/base/agent_api/README.md`, "MCP Apps"; the first is `apps/base/software/card/`).
- A list keeps its page, search, filters, sort and page size in the URL through `ListState`; keep a module's existing query names and page sizes. A private `to_int` or `parse_page` is the copy `Params` and `ListState` replaced.
- A page's write event calls its operation contract through `PageContracts` (`submit`, or `preview`/`commit` for a confirmation) and is declared in the service's `PageWrites`, not a facade call: the host refuses a business write the declaration does not cover, and a module not yet migrated keeps a `Pending` allowance with its reason. Personal view state (columns, arrangement, theme, pins) opens `MutationBoundary::begin_view_state`. Contract: `apps/base/agent_api/README.md`.
- To ask the account holder for a fresh second-factor check before an operation, declare it with `bilibi_step_up::declare!` in your own module and call `StepUp::require` from your facade (`apps/base/step_up/README.md`). Never decide in code whether it applies, never import the authenticator, and never let the step-up or two-factor modules name your module. An action that changes the server itself declares `.always()` (a code every time, Dev included); do not test `BILIBI_ENV` or `StepUp::enforced` in an owner to get that.
- What the running program is made of (Platform and Domain versions) is `bilibi_module_registry::Composition`, which the host hands in as the `bootstrap.composition` service; a Base module takes it from there (`base/software` does) and never reads a pin file, a tag or the catalogue to learn what is installed.
- An agent's self-reported `harness/model-version-effort` is `bilibi_tenancy::SelfReport`, read from `Scope::agent()` or the recorded `agent_self_report`. Show it under `SelfReport::LABEL` and never decide anything on it; the parse and the header belong to the agent edge (`apps/web/README.md`).
- Which instance a page or confirm step is on (Dev, Staging, Production), its label and colour come from `bilibi_base::system::Instance::resolve` (`apps/base/system/README.md`), whose role is the `instance.role` setting (initialized from `BILIBI_ENV` at install). Never read the variable, a setting or the origin yourself to decide it, and never add a second identity source.
- The installer (`apps/installer`) runs outside the program, writes its own tables with its own connection and never inserts audit rows or notifications by hand; the owning module settles the outcome into the audit trail when the server next looks (`apps/base/software/README.md`, "How a worker plugs in", item 7). Do not add a second settle loop or a worker-side audit insert. The one exception is the installer carrying existing evidence rows (`base_audit_actions` `software.*` and `step_up.*`, `base_audit_mutations` of `base/software.job`) across a database restore unchanged, with their ids and times, so the audit trail of an Undo and of the carried jobs survives (`apps/installer/README.md`, "Caveats"); it creates no audit row of its own.
- A file the program and the installer hand to each other (a release on its way in) goes under the instance's `incoming/` (`bilibi_software::InstancePaths`, `scripts/install-server.sh`), never `data/` (the installer cannot read it) or `releases/` (the program cannot write it); the program's unit allows only those two folders.
- Message kind follows the outcome: `Success` only for a completed write, `Info` informs, a refusal names its real cause. Kinds and timing: `DESIGN.md` "Dialogs and feedback".
