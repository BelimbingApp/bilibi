# Tenancy identity boundary

Use `Authentication` and `Scope` from `src/lib.rs` for authenticated identity. Raw route IDs and K0 party IDs carry no authority. Scope and Actor have private identity fields, no deserialize implementation and no public constructor; the display fields are never policy input. A proof applies to one freshly guarded unit of work, not a permanent credential.

`base/tenancy.authentication` owns a once-bound `ActorVerifier`. Core User installs the account adapter during registry boot; missing and duplicate bindings fail startup. The `ProofClient` read adapter keeps owner checks on the caller's connection or transaction. `ReadClient` extends it with `query` for owners that also read lists (Settings reads take `&dyn ReadClient`). Base has no SQL against Core account/company/person tables. `Authentication::authenticate` is an authentication-edge API: supply only identities extracted from validated durable credentials, never request IDs. It establishes identity and grants no capabilities. `Scope::mutation_context` supplies F2 attribution from that identity.

`base/tenancy.parties` owns optional `OrganisationProvider` and `PersonProvider` bindings. K1/K7/K9 install owner adapters using K0's `bilibi-party-ids`. Missing providers refuse all target proof requests. Providers must prove live, eligible targets in the exact scope, including tenant and access checks; IDs and business relationship roles never grant authority. An organisation/person proof retains its scope and typed target ID. The account adapter (`bilibi_user::standing`) proves a staff account's stored Person and a customer account's stored Person, affiliation and company through their owners on every authentication. Workplaces are proved separately through explicit desks. This boundary neither fabricates Person data nor depends on People.

`prove_operator` returns a sealed proof only when the live scope tenant is explicitly recorded in the singleton `platform_operator` table. Numeric tenant IDs and `grant_all` have no operator meaning. Migration `005-tenancy-operator` leaves the marker unset; `bilibi-web platform-provision`, `bilibi-web create-owner` and the development `seed` set it through `provision_platform_operator`; `platform_operator` reads the marked tenant. Operator proof establishes identity, not a permission grant: use Authz `authorize_operator` for an operation that requires both. The migration does not replay the historical tenancy schema in `001-base`.

`prove_owner` proves the installation owner named by Core User's bootstrap receipt (`user_bootstrap`). It re-reads the account, eligibility, receipt and operator marker on the caller's connection every time. An agent can hold that person's standing while its grant remains live; an impersonated session never can. No role or capability confers ownership. `Authentication` carries the bound verifier into each sealed scope so an old scope cannot retain revoked standing. Core Agent Access binds `AgentVerifier`: every reproof checks the connection's tenant, person, organisation, expiry and revocation against the refreshed actor. Missing bindings refuse agent proofs. Reviewed commits also hold the credential row through the existing plan authority, preventing revocation from racing the write. Owner-only actions still require their declared Base Step-up policy.

## The current company

`Scope::current_company()` is the company a browser request works in: the session's chosen company (`sessions.company_id`, chosen in the shell's top bar) while the account still reaches it, else the remembered valid desk, the first live desk, or no desk. `authenticate_session` takes the stored choice and keeps it only when the bound `ActorVerifier::reaches_company` confirms it on the same connection (Core User answers through Core Company's `reachable`). The browser-session edge additionally supplies a one-way credential digest to `ActorVerifier::reaches_session_company`, so the identity owner can enforce company-specific sign-in policy for chosen, fallback and explicit operational target desks without exposing the bearer token. `reprove` proves work access again without reconstructing browser credentials. The choice grants nothing and never changes the actor. Work access comes only from explicit staff desks; company-record administration retains its separate reach and capabilities. Agent scopes do not use a browser session choice: a qualified provider credential carries its exact provider workplace, while ordinary OAuth resolves the account's remembered or first live desk; an explicit operational target is re-proved as an exact live desk. A system principal has no desk. `OrganisationDirectory::reachable` and `PartyProofs::reachable_organisations` list the companies the actor may work in, for the top bar. Decision: [ADR 19](../../../docs/architecture/decisions/19-company-work-access-and-page-scope.md); the owner contract is [Core Company's](../../core/company/README.md#the-current-company).

## Organisation summaries

`OrganisationDirectory` and `PartyProofs` return `NamedOrganisation` with `id`, display `name`, full `status` and the existing `archived` flag. Core Company populates both status fields through the same scoped directory reads. See [Core Company's public summary contract](../../core/company/README.md#public-company-summaries) for lifecycle values, authorization, chooser policies and custom directory updates.

**`PartyProofs::primary_organisation(client, scope)` names the tenant's live primary company** (Company's `OrganisationDirectory::primary`, defaulting to none): the company whose settings govern records that belong to no one company, such as a retention sweep's.

## Named system principals (SP1)

`Authentication::for_principal(client, tenant, principal)` is the trusted worker edge: it seals a `Scope` whose `Actor` is the named system principal, in a live tenant, with no account, person, organisation, affiliation, agent facet, impersonator or step-up code and a fresh CSRF value. Call it through Authz's `SystemAuthentication::for_system(client, &SystemScope)`, which proves the declaration first; Queue does this on every attempt of a system job, so `Execution::scope()` is `Some` for a principal too. It is never a browser constructor and never deserialized: the principal comes from a worker's rehydrated job row or a schedule definition.

- `Scope::principal()` / `Actor::principal()` name it; `Scope::user()` is `0`, an id no account has, so every user-shaped read (roles, direct grants, ownership, user settings) matches nothing. Authz field restrictions are the exception and fail closed: every restriction in the tenant applies to a principal (`apps/base/authz/README.md`). The principal holds exactly the capabilities an administrator granted it by name (`Grants::set_system`), decided live by Authz's named-principal rule on every `decide`/`authorize_key`.
- `Scope::mutation_context` attributes its writes `System · <principal>` (`Context::system`), and Audit's `Attribution::from_scope` records the same. Core Person and Affiliation keep refusing a system-attributed write; a principal's work is what their owners allow a system actor.
- `reprove` re-seals it against the live tenant; `prove_operator`, `prove_owner` and `confirm_password` refuse it: operator and owner standing are an account's. Grant administration refuses it (`Grants`).
- `Authorization::authorize_scope(client, scope, key)` is the decision seam for a module below Authz (Settings) that must enforce a capability on a sealed scope, principal or account; Authz binds it beside `authorize_operator`.

Impersonation (K14): `authenticate_session` takes the operator the durable session row names (`sessions.impersonator_id`) and re-proves that account live in the same tenant beside the actor; `Scope::impersonator()` then carries it, and `mutation_context` and Audit's `Attribution::from_scope` record the actor/impersonator pair. The viewed account must still have each workplace desk. The operator's already authenticated live session satisfies workplace company sign-in during authorized impersonation, without a target-provider session. To refresh a scope an edge already sealed, call `Authentication::reprove(client, scope)`, not `authenticate(tenant, user, csrf)`: the latter drops the operator (and the agent facet), so the owner's writes would lose half the audit pair. Self-service writes of the account's own preferences, pins, credentials re-proof and agent connections refuse a scope with an impersonator.

Agent self-report (ADR 01): `SelfReport` is an agent's `harness/model-version-effort`, shape-checked by `SelfReport::parse` and sealed on the agent facet by `Scope::for_agent`. `mutation_context` copies it to `Context::agent_self_report` and Audit's `Attribution::from_scope` records it. It is evidence shown under `SelfReport::LABEL`, never authority.

## Tenant data and provisioning

### Child-granted parent oversight

`Oversight` (`base/tenancy.oversight`) owns child consent. `given` reads only the caller's recorded parent and consent under `admin.tenancy.oversight.view`; `set_in` replaces it under `admin.tenancy.oversight.manage` on the child's mutation transaction, checks the expected version and returns a `Change`. Activating or widening requires the floor operation `base.tenancy.oversight.grant`. Narrowing and revocation never require a factor. Neither an operator action nor a parent capability creates consent.

`prove` requires `tenancy.oversight.view` and a live linked staff person, excluding system principals and impersonation. Its sealed `OversightScope` contains only active, unexpired consenting direct children, bounded at 500 before Grid's smaller operator limit. `verify` rechecks the reader, capability, both tenants, recorded hierarchy, expiry and exact grant version. It returns the refreshed **parent** scope, never child membership. Use this proof only through Grid's audited oversight facade; ordinary owner reads and writes still take `Scope`.

`Tenants` (`base/tenancy.tenants`, `src/admin.rs`) owns tenant identities and the audited tenant insert. Its directory methods take an `OperatorProof`; numeric tenant IDs and `grant_all` never confer standing. `search` bounds each page to 100 rows. `TenantIdentity` includes the explicit operator marker, parent, name and status.

- `principal_page` lists live tenants in id order (at most `PRINCIPAL_PAGE_MAX` per page, bounded by a `through_id` high-water mark) for a system principal's worker in the operator tenant; it decides `admin.tenancy.tenant.list` on the principal's own scope. Schedule's per-tenant fan-out is its caller ([ADR 17](../../../docs/architecture/decisions/17-per-tenant-scheduled-work.md)).
- `create_in` rechecks operator standing and `admin.tenancy.tenant.create` on the caller's mutation transaction through `Authorization::authorize_operator_in`. It returns field errors or a sealed `CreatedTenant` receipt.
- The receipt proves only the tenant this transaction just inserted. It is bound to the PostgreSQL transaction and the original tenant and actor. It cannot be reused in another transaction or authorize access to an existing tenant.
- Core Company's provisioning facade accepts that receipt to insert companies and assign the primary company on the same audited transaction. It never retargets a `Scope`.
- Deployment commands retain the explicit `provision_tenant`, `provision_platform_operator` and `platform_operator` seams. They are not request handlers.

## Tenants page and operations

[Core Tenant Administration](../../core/tenant_administration/README.md) composes the `/tenancy/tenants` page, search/read contracts and the reviewed tenant-and-companies create contract above Tenancy, Company and Agent API. Base Tenancy stays below those modules and owns no page adapter.

The existing authorization rule is shared by browser and agent: the list requires operator standing and `admin.tenancy.tenant.list`; create requires operator standing and `admin.tenancy.tenant.create`. These platform capabilities are declared by Authz on Tenancy's behalf. `Authorization` is the once-bound seam into Authz; missing and duplicate bindings refuse startup. An agent acts for its person's live standing and capabilities, with direct denials preserved.

Creation requires the tenant's name and primary company name; optional additional companies, parent and active/suspended status are reviewed together. The contract declares its Base Step-up operation. Every tenant, company and primary assignment is returned as a `Change` on one transaction, attributed to the person with the agent connection in the committed action. Failure leaves none of those rows behind.

`ClientIdentity` is bounded printable transport evidence, separate from `SelfReport`. The host attaches it with `Scope::with_client_identity`; `mutation_context` carries it to write audits. It changes no actor, grant or permission.

`Authentication::account_identity(client, scope, account)` supplies live account and Person evidence for a routing or independence check in the scope's tenant. It seals no credential and grants no authority. Callers must still apply company reach, owner visibility and capability checks; never turn this evidence into an acting scope.

`Authentication::reprove` preserves the queued-job channel as well as agent, impersonator and presented 2FA evidence. Refreshing identity must never turn background work into a browser action.

## Linked party identities and code lookup

`PartyProofs::party_identity(client, scope, PartyId)` reads the fixed Core code, display name and lifecycle status of a Company or Person on the caller's connection. The caller must authorize the linked record it is displaying first. These identity facts need no separate Company or Person view permission, as with the existing company-name seam. The result contains no contacts, tax or registration facts; those still use the Core owner's capability and field masks. A missing owner, removed record or another tenant's ID returns `NotFound`, never a blank code or placeholder name. Identity is display evidence, not permission or eligibility to write.

`PartyProofs::parties_by_codes(client, scope, codes)` resolves an exact set of stored codes for both Core kinds in one facade call, with at most one query per installed owner. Input is bounded by `PARTY_CODE_LOOKUP_LIMIT` (10,000 codes including duplicates); blank, overlong or null-containing codes and an oversized request return `Invalid`. An empty request returns no results. Duplicate inputs are folded; unknown and other-tenant codes are omitted. Company and Person can share a code, so keep `PartyIdentity::record_kind()` and `record_id()` together. Archived companies and retired people remain identifiable. Callers filter the results through their own authorized linked records and report unknown codes against the requesting row. Each Core owner binds its `PartyIdentityProvider`; Base never reads Core tables.

On a fresh disposable database, `BILIBI_PARTY_PROOF=disposable cargo run -p bilibi-person --example party-identities` proves code collisions, tenant isolation, identity access with Core views denied, contact protection, retirement and both sides of the batch bound.

`Authentication::authenticate_job` is the trusted Queue edge: it keeps the captured desk exactly and refuses lost access. `require_work_company` re-proves an explicit staff workplace on the owner's connection, independently of the selected desk, for owners such as Artifacts; browser scopes also prove that the session satisfies that workplace's company sign-in policy, while trusted nonbrowser and captured-job scopes keep their existing desk proof. Neither accepts a company ID as authority.
