# Base Custom Fields

`base/custom_fields` owns tenant-specific definitions for record types that opt in through `RecordType`. The record owner continues to store values in its own JSONB column and validates every submitted patch inside its write transaction.

The public facade is `base/custom_fields.fields`. It lists definitions and supports define, update, archive, restore and owner-side validation. Definition writes use `MutationBoundary`, require `admin.custom.fields.manage` and the opted-in record type's capability, and enforce immutable keys and types. `active_for_record` returns current tenant definitions to an already-authorized owner page without requiring definition-management permission; `active_for_record_on` reads definitions through the caller's transaction for scoped Agent API schemas. The owner route must authorize its create or view operation first.

Choice values are stable codes; an option with `active: false` is retired and remains valid only when preserving an existing value. Grid and Authz consume typed runtime-provider contributions from this module. They load active definitions per scope on each request, expose them as `cf_<key>` fields, and bind JSON keys as values in Grid SQL. Reference fields name an opted-in Grid table with a `ReferenceTargetProvider`; choices, resolution and write validation run for the current scope on the caller's connection. Providers return only live targets the actor may read, and provider failures refuse the operation.

The owner opt-in and Grid/Authz runtime provider contracts are described in [ADR 05](../../../docs/architecture/decisions/05-tenant-defined-custom-fields.md). Core Company is the first adopter. Reporting and shared exports are out of scope.

Grid supports runtime projection, text search and bound root-field expressions for owner sorting and filtering. Authz uses tenant definitions in field restriction management and audit history masking. The tenant administration page at `/custom-fields` lists active and archived definitions for opted-in record types and supports create, edit, archive and restore. Reference target types are offered only when an opted-in owner contributes a resolver; the target type cannot change after creation. Choice options are edited as JSON and keep their stable codes and retired-option metadata.

Definition mutations from this page use the facade's audited `MutationBoundary` methods under a declared, event-scoped `Pending` page-write allowance. They do not yet have Agent API operation contracts; definition management operations remain follow-up work. Company is the first reference target provider. Company create, custom-field agent writes and detail pages resolve or validate target keys against the actor's readable companies, while Grid projections and audit diffs withhold target keys the actor cannot currently read. Tenant administrators configure the active-field, text-length and custom-JSON byte limits in Tenant Settings. Defaults are 100 fields per record type, 100,000 text characters and 1 MiB; allowed ranges are 1–1,000 fields, 1–1,000,000 characters and 1 KiB–16 MiB. Lowering a limit does not rewrite stored values, but updated values and the resulting custom object must satisfy the current limits.
